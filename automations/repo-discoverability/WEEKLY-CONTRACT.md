# repo-discoverability — 周报契约

这个文件规定**消费端（DSH 会话）拿到 issue 后，周报必须长什么样**。

它约束的是**生成周报的那个 agent**，不是采集脚本。

> **这个文件是权威版本。**
> 定时任务里的提示词只负责说「读这个文件并照做」——
> 提示词存在 DSH 自己的存储里，跟本仓库没有自动关联。
> **结构一变，改这一个文件就够，提示词不用动。**
> 但提示词里如果写死了某一节的名字，改名时**要同步改**。

---

## 1. 数据来源约束

数据**只来自本地读取脚本**，不重新审计、不联网判断：

```bash
python3 ~/Documents/workplace/ai-capability-store/automations/repo-discoverability/report.py --days 7
```

它读的是 GitHub 上**已经开出来的 issue**（带 `discoverability` 标签 + bot marker）。

- **这些是上周已经落地的单，不是新发现。** 有新发现说明云端 workflow 没跑 —— 要指出来，不要当成刚发现。
- 脚本失败（`gh` 未授权 / 网络）→ **直接说错误**，不要凭记忆编条目。
- 输出 JSON 里 `counts.behind = 0` → 正常报告「全部合规」，不要硬凑。

---

## 2. 周报的四段

顺序固定，**每段用自己的名字，不用编号代称。**

```
一、总览
二、不合规仓库（按待补项数排序）
三、必修 vs 建议（分开统计）
四、建议动作
```

---

### 一、总览

**一行说完**，必须包含三个数：

```
本周 5 个仓库中 4 个不合规，合计 6 项待补，1 个合规。
```

数据来自 `counts.behind` / `counts.failures_total` / `counts.clean`。

---

### 二、不合规仓库

按**待补项数从多到少**排，最多 10 个。每行写：

```
LyraWang6688/feishu-retail-ops  #862  3 项  D3 README 前三行 · D4 llms.txt · D6 DSH badge
```

- 仓库名 + issue 号 + 项数 + 具体哪几项
- **超过 10 个**：只列前 10，末尾写「另有 N 个未列出」

---

### 三、必修 vs 建议

**必须分开**，先说必修：

| | 来源 | 含义 |
| --- | --- | --- |
| **实测项（必修）** | `failures[].tier == "实测项（必修）"` | 有测量证据的项（D1 / D2 / D3） |
| **生态约定（建议）** | `failures[].tier == "生态约定（建议）"` | 无直接测量的项（D4 / D5 / D6） |

统计格式：

```
必修 3 项：D3 × 3
建议 3 项：D6 × 2 · D4 × 1 · D5 × 1
```

**为什么分开**：必修项是真的会影响被搜到，建议项只是补齐规范。混在一起会让人误以为六项同等重要。

---

### 四、建议动作

**0–2 个动作。** 真值得才写，没有就写「本周没有必须立刻处理的」。

每个写：**做什么 / 为什么是现在 / 第一步**。

优先从这两类里挑：

- **必修项集中在同一个仓库** → 那个仓库最该先修
- **同一个必修项出现在 ≥3 个仓库** → 说明是共性问题，可能要改规范本身

---

## 3. 通用约束

- **不重新审计**：只读 issue，不判断「对错」，标准在
  [`MAINTAINER-GUIDE.md`](./MAINTAINER-GUIDE.md)，校验在 `audit_discoverability.py`
- **不写任何仓库**：本自动化只读 + 开 issue。周报里不要承诺「我去改」
- **数字要能指回 issue**：每个判断都要能指到具体 issue 号
- **issue 修好后会自动关闭**，所以本期没出现的仓库 = 已合规，不用特别说明
- **归档仓库不在范围内**（只读），不要提议去改它们
