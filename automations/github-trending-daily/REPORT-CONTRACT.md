# github-trending-daily — 报告契约

这个文件规定**消费端拿到云端快照后，报告必须长什么样**。

它约束的是 **DSH 会话里生成报告的那个 agent**，不是本目录的采集脚本
（采集脚本的契约在 [`README.md`](./README.md) 的 "Output contract"）。

> **这个文件是权威版本。**
> 定时任务里的提示词（本机 `~/.dsh/storages/schedule.json`）是它的实例化 ——
> 提示词存在 DSH 自己的存储里，跟本仓库没有自动关联，改了提示词不代表这里自动更新，
> 反过来也一样。**结构一变，两边都要改，并且先改这里。**

---

## 1. 数据来源约束（不可协商）

- 数据**只来自 `data` 分支**（云端采集）。本地不跑采集脚本、不做网络抓取。
- 先跑 `sync_from_cloud.py --days 7 --json`，看 `today_available`。
- `today_available = false` → 直接说「今天云端数据缺失」，给出诊断方向
  （去 Actions 看 `automation-github-trending-daily` 的最近一次运行）。
  **不许用昨天的数据冒充今天，不许编任何数字。**
- 报告开头必须标明：`数据来源：云端（data 分支） · 采集于 YYYY-MM-DD HH:mm`

## 2. 两个维度（**双向映射，顺序不能乱**）

```
维度一（社区 → 我）：社区在关注什么、在解决什么问题、和我有什么关联
维度二（我 → 社区）：我关注的方向上，社区有没有人在做相似的事
```

**这不是「四个段落」，是两个相反方向的映射。** 写反了，报告就退化成清单。

---

### 维度一：社区在关注什么

#### 1.1 他们在关注什么（3-5 个话题）

用 `topic_frequency` 和 `trend_gain` 支撑。每个话题写：叫什么、哪几个项目在涨、涨多快。

**只讲社区，不要掺「我」。**

#### 1.2 他们在解决什么问题

每个话题一个底层问题，一句话。

**不要复述项目描述** —— 要说「它在解决谁的什么痛」。

- ❌ 反例：「X 是一个 agent skills 框架」= 复述，没信息量
- ✅ 正例：「agent 装了一堆 skill 后互相冲突、不知道怎么选」

#### 1.3 这些和我的关注有什么关联

把 1.1 的**每个话题**都过一遍，映射到关注清单里的方向。

**无关的也要写「无关」** —— 那是判断结果，跳过就不知道判过了。

```
【话题】→ 关联方向：[方向名]（core/watch）／ 无
　关联类型：补充（给我缺的那块）／ 替代（我已有方案可换）／ 印证（验证我在做的对）／ 无关
　一句话：具体关联在哪，指到仓库或能力
```

---

### 维度二：我关注的方向上，有没有人在做相似的事

**这是反向映射：从我的方向出发，去社区里找「做类似事情的人」。**

按关注清单过，**只过 `core`**（`watch` 有亮的才提，`observe` 不主动提）：

```
【方向名】
　我的进展：有 / 没有 —— 证据（仓库 + 数字）／ 或说明为什么这些不算进展
　有没有人在做相似的事：
　　· 有 → 谁（指到仓库）、做到哪一步、和我做的是同一件事还是相邻的事
　　· 没有 → 明写「没看到」
　一句话处境：领先（我早于社区）／ 同步（大家都在做）／ 落后（社区热我没跟）／ 无人区（都没动静）
```

**为什么「有没有人在做相似的事」比「我的进展」更重要：**

> 它回答的是 —— **我这条路是不是已经有人走通了，或者正在被人挤爆。**

所以宁可多写一句「谁在做、做到哪」，也不要只写「有」或「无」。

**「落后」最有价值**：社区热而我不在跟时必须点出来，
**不要因为那个方向不在关注清单里就跳过** —— 发现了新的热门方向，也写进来。

允许大部分是「今天没有」—— 那本身就是信息，不要硬扯。

## 3. 关注清单

维度一 1.3 和维度二 整段都依赖一份**关注清单**，格式见
[`interests.example.yaml`](./interests.example.yaml)。

- 真实清单**不进仓库**（个人上下文，且仓库公开），放在
  `~/.automation-state/github-trending/interests.yaml`。
- 三级：`core`（必须给结论）/ `watch`（有亮点才提）/ `observe`（只在特别相关时提）。
- **用户表达新的关注方向时，先更新清单，再产报告。**
- 防腐：某个 `core` 连续多日「没看到有人在做 + 我也没进展」→ 提醒降级或删除。

## 4. 收尾：值得动手的（0-3 个）

真值得才写，没有就写「今天没有值得动手的」。

每个写：**做什么 / 为什么是现在 / 第一步动作**。

优先从「落后」（社区热我没跟）和「领先」（我早于社区）里挑；
同步和无人区通常不急着动。

## 5. 通用约束

- 话题分析基于 `topic_frequency` 和 `trend_gain`，不凭感觉
- 每个判断都要能指回具体仓库
- **星多不等于无关**（反例：`morluto/rea` 31 万星，但 topics 有 `dsh-plugin`）；
  **星少也可能关键**
- MCP / CLI 只是形态，看能力本身 —— 操作者有 bash，大多数 MCP 是冗余的
- **自动化方案的稳定性优先级：API > 协议/CLI > UI 元素树 > 截图视觉**
  - GUI 方案只在对方没有 API 时才值得考虑
  - 采用 GUI 方案时要提示「对方开放 API 后应迁走」
- 之前推荐过的项目跳过
- **不要自动写飞书 Base** —— 收录必须等人确认

## 6. 周报的差异

同一套两维度，差异在判据：

| 位置 | 日报 | 周报 |
| --- | --- | --- |
| 1.1 | `topic_frequency` + `trend_gain` | `topics_persistent` vs `topics_emerging`，看 `days_present` |
| 维度二「我的进展」 | 当日数字 | **`star_delta`（一周净增）**，不用 `peak_daily_gain`（单日易被爆点误导） |

周报额外要看**跨周方向性变化**：

- 某个 `core` 连续几周「没看到有人在做 + 我也没进展」→ 判断是自己太早，还是确实没需求
- 连续几周「有越来越多人在做」→ 赛道在变热，要加速或被淹没
- 连续几周「落后」→ 该补上或明确放弃
- 某个 `core` 连续 3 周以上「无人区 / 落后」→ 建议降级或从清单删除

**这类判断日报告诉不了，是周报存在的理由。**

周报前必须看聚合结果的 `trustworthy`：为 `false` 时只报「本周数据不足 N 天，
趋势判断不可靠」，**不硬做结论**。
