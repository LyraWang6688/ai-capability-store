# github-trending-daily — 报告契约

这个文件规定**消费端拿到云端快照后，报告必须长什么样**。

它约束的是 **DSH 会话里生成报告的那个 agent**，不是本目录的采集脚本
（采集脚本的契约在 [`README.md`](./README.md) 的 "Output contract"）。

> **为什么单独成文**：这份结构最初只活在 DSH 定时任务的提示词里
> （本机 `~/.dsh/storages/schedule.json`）。机器一换或 DSH 重装就没了，
> 也无法 review、无法复现。写进仓库，结构才可版本化。

---

## 1. 数据来源约束（不可协商）

- 数据**只来自 `data` 分支**（云端采集）。本地不跑采集脚本、不做网络抓取。
- 先跑 `sync_from_cloud.py --days 7 --json`，看 `today_available`。
- `today_available = false` → 直接说「今天云端数据缺失」，给出诊断方向
  （去 Actions 看 `automation-github-trending-daily` 的最近一次运行）。
  **不许用昨天的数据冒充今天，不许编任何数字。**
- 报告开头必须标明：`数据来源：云端（data 分支） · 采集于 YYYY-MM-DD HH:mm`

## 2. 三个维度（**漏斗，不是清单，顺序不能乱**）

```
① GitHub 在关注什么       ← 现象层，纯社区视角
② GitHub 在解决什么问题   ← 本质层，纯社区视角
③ 和我关注的有什么相关     ← 映射层，我的视角（需要关注清单）
```

### ① GitHub 在关注什么（3-5 个话题）

用 `topic_frequency` 和 `trend_gain` 支撑。每个话题写：叫什么、哪几个项目在涨、涨多快。

**这一节只讲社区，不要掺「我」。**

### ② GitHub 在解决什么问题

每个话题一个底层问题，一句话。

**不要复述项目描述** —— 要说「它在解决谁的什么痛」。

- ❌ 反例：「X 是一个 agent skills 框架」= 复述，没信息量
- ✅ 正例：「agent 装了一堆 skill 后互相冲突、不知道怎么选」

### ③ 和我关注的有什么相关

**从社区话题出发，看它触到我哪个关注 —— 不是从我的关注出发做巡检。**

分两小节写，都要有：

#### 3.1 话题 → 我的关注（逐个话题映射）

把 ① 的每个话题都过一遍，**无关的也要写**（写「无关」本身就是判断结果）：

```
【话题】→ 关联方向：[方向名]（core/watch）／ 无
　关联类型：补充（给我缺的那块）／ 替代（我已有方案可换）／ 印证（验证我在做的对）／ 无关
　一句话：具体关联在哪，指到仓库或能力
```

⚠️ 不许跳过任何一个话题 —— 跳过就不知道你判过了。

#### 3.2 我的关注方向 → 进展与处境（只过 core，watch 有亮点才提）

```
【方向名】
　我的进展：有 / 没有 —— 证据（仓库 + 数字）／ 或说明为什么这些项目不算进展
　社区动静：热 / 温 / 无 —— 有没有相关话题或仓库在涨
　处境：领先 / 同步 / 落后 / 无人区
```

**处境怎么落（2×2）：**

|              | 社区没动静 | 社区也在做 |
| ------------ | ---------- | ---------- |
| **我在做**   | 领先 —— 早期机会，也可能是死路 | 同步 —— 看别人怎么解，别闭门造车 |
| **我没跟**   | 无人区 —— 自己判断值不值得走   | 落后 —— 最该警惕，要么补上要么明确放弃 |

⚠️ **「落后」这一格最有价值**：社区热而我不在跟时必须点出来，
**不要因为不在关注清单里就跳过**。

⚠️ 允许大部分是「今天没有」—— 那本身就是信息（这个方向今天没动静），不要硬扯。

## 3. 关注清单

`③` 完全依赖一份**关注清单**，格式见 [`interests.example.yaml`](./interests.example.yaml)。

- 真实清单**不进仓库**（是个人上下文，且仓库是公开的），放在
  `~/.automation-state/github-trending/interests.yaml`。
- 清单分三级：`core`（必须给结论）/ `watch`（有亮点才提）/ `observe`（只在特别相关时提）。
- **用户表达新的关注方向时，先更新清单，再产报告。**

## 4. 值得动手的（0-3 个）

真值得才写，没有就写「今天没有值得动手的」。

每个写：**做什么 / 为什么是现在 / 第一步动作**。

优先从「落后」（社区热我没跟）和「领先」（我早于社区）里挑；
同步和无人区通常不急着动。

## 5. 通用约束

- 话题分析基于 `topic_frequency` 和 `trend_gain`，不凭感觉
- 每个判断都要能指回具体仓库
- **星多不等于无关**（反例：`morluto/rea` 31 万星，但 topics 有 `dsh-plugin`）；
  **星少也可能关键**
- MCP / CLI 只是形态，看能力本身 —— 操作者有 bash，大多数 MCP 是冗余的
- **自动化方案的稳定性优先级：API > 协议/CLI > UI 元素树 > 截图视觉**
  - GUI 方案只在对方没有 API 时才值得考虑
  - 采用 GUI 方案时要提示「对方开放 API 后应迁走」
- 之前推荐过的项目跳过
- **不要自动写飞书 Base** —— 收录必须等人确认

## 6. 周报的差异

同一套三维度，差异在判据：

| 维度 | 日报 | 周报 |
| --- | --- | --- |
| ① | `topic_frequency` + `trend_gain` | `topics_persistent` vs `topics_emerging`，看连续几天 |
| ② | 同上 | 同上 |
| 3.2 进展 | 当日数字 | **`star_delta`（一周净增）**，不用 `peak_daily_gain`（单日易被爆点误导） |

周报额外要看**跨周方向性变化**：

- 某个 core 方向连续几周「领先」→ 判断是自己太早，还是确实没需求
- 连续几周「落后」→ 该补上或明确放弃
- 某个 core 连续 3 周以上「无人区 / 落后」→ 建议降级或从清单删除

**这类判断日报告诉不了，是周报存在的理由。**

周报前必须看聚合结果的 `trustworthy`：为 `false` 时只报「本周数据不足 N 天，
趋势判断不可靠」，**不硬做结论**。
