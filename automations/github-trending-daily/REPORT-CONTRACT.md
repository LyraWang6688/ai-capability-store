# github-trending-daily — 报告契约

这个文件规定**消费端拿到云端快照后，报告必须长什么样**。

它约束的是 **DSH 会话里生成报告的那个 agent**，不是本目录的采集脚本
（采集脚本的契约在 [`README.md`](./README.md) 的 "Output contract"）。

> **这个文件是权威版本。**
> 定时任务里的提示词（本机 `~/.dsh/storages/schedule.json`）只负责说「读这个文件并照做」——
> 提示词存在 DSH 自己的存储里，跟本仓库没有自动关联。
> **结构一变，改这一个文件就够，提示词不用动。**

---

## 1. 数据来源约束（不可协商）

- 数据**只来自 `data` 分支**（云端采集）。本地不跑采集脚本、不做网络抓取。
- 先跑 `sync_from_cloud.py --days 7 --json`，看 `today_available`。
- `today_available = false` → 直接说「今天云端数据缺失」，给出诊断方向
  （去 Actions 看 `automation-github-trending-daily` 的最近一次运行）。
  **不许用昨天的数据冒充今天，不许编任何数字。**
- 报告开头必须标明：`数据来源：云端（data 分支） · 采集于 YYYY-MM-DD HH:mm`

## 2. 采集层是中立的，分类是分析层的事

采集脚本按它自己的标准（`trend_gain` 排序、噪音过滤、新仓库门槛）产出一份
**中立的候选清单**，它**不知道飞书收录表里有什么**。

所以分析开始前必须先做一步**分类**：

| 组 | 判据 | 去哪 |
| --- | --- | --- |
| **已有项目** | `Project` 出现在飞书「GitHub 优质项目收录」表里 | 板块二 |
| **新增项目** | 不在表里 | 板块一 |

读表方式：用 `repo-collector` skill 的 `scripts/target.json` 里的
`base_token` / `table_id`（收录表坐标），跑 `lark-cli base +record-list --as user`。

---

## 3. 报告结构：两个板块

```
板块一：新增（两个维度，双向映射）
  维度一（社区 → 我）：社区在关注什么、解决什么问题、和我有什么关联
  维度二（我 → 社区）：我关注的方向上，社区有没有人在做相似的事

板块二：已有项目 · 状态跟踪
  采集数据里匹配到的、已经在收录表中的项目 —— 它们今天有什么变化
```

---

### 板块一：新增（只含**不在**收录表里的项目）

#### 维度一：社区在关注什么

**1.1 他们在关注什么（3-5 个话题）**

用 `topic_frequency` 和 `trend_gain` 支撑。每个话题写：叫什么、哪几个项目在涨、涨多快。
**只讲社区，不要掺「我」。**

**1.2 他们在解决什么问题**

每个话题一个底层问题，一句话。**不要复述项目描述**，要说「它在解决谁的什么痛」。
- ❌「X 是一个 agent skills 框架」= 复述
- ✅「agent 装了一堆 skill 后互相冲突、不知道怎么选」

**1.3 这些和我的关注有什么关联**

把 1.1 的**每个话题**都过一遍，映射到关注清单里的方向。**无关的也要写「无关」**。

```
【话题】→ 关联方向：[方向名]（core/watch）／ 无
　关联类型：补充 / 替代 / 印证 / 无关
　一句话：具体关联在哪，指到仓库或能力
```

#### 维度二：我关注的方向上，有没有人在做相似的事

**反向映射：从我的方向出发，去社区里找「做类似事情的人」。**

按关注清单过，**只过 `core`**（`watch` 有亮的才提，`observe` 不主动提）：

```
【方向名】
　我的进展：有 / 没有 —— 证据（仓库 + 数字）
　有没有人在做相似的事：
　　· 有 → 谁（指到仓库）、做到哪一步、和我做的是同一件事还是相邻的事
　　· 没有 → 明写「没看到」
　一句话处境：领先 / 同步 / 落后 / 无人区
```

**为什么「有没有人在做相似的事」比「我的进展」更重要**：
它回答的是 —— **我这条路是不是已经有人走通了，或者正在被人挤爆。**

**「落后」最有价值**：社区热而我不在跟时必须点出来，
不要因为那个方向不在关注清单里就跳过。

---

### 板块二：已有项目 · 状态跟踪

**只写采集数据里真正匹配到的项目。** 对每一个：

```
【仓库名】
　今天：trend_gain +N 星（现 ⭐X）
　话题：命中的 topics
　和收录表比：表里 Stars 记的是 ⭐Y —— 判断「收录后涨了」还是「基本没动」
　一句话：还在涨（趋势成立）/ 平了 / 该考虑降级或删掉
```

⚠️ **如果今天采集没覆盖到任何已收录项目，就明说一句**：
「今天采集没覆盖到你收录的项目」——
不要假装有数据，也不要为了填满这一节去现查（那是另一个自动化的事）。

⚠️ **板块二的覆盖率有限**：采集层里有一份硬编码的已收录名单，命中的会被丢弃，
所以能匹配到的通常是「名单之外」的那部分收录项目。**这是已知限制，不是 bug。**

---

## 4. 值得动手的（0-3 个）

真值得才写，没有就写「今天没有值得动手的」。

每个写：**做什么 / 为什么是现在 / 第一步动作**。

优先从「落后」（社区热我没跟）和「领先」（我早于社区）里挑；
同步和无人区通常不急着动。

## 5. 关注清单

维度一 1.3 和维度二 整段都依赖 `interests.yaml`（同目录，schema 在文件内注释里）。

- 清单**就在本仓库**：内容是技术方向 + 已公开的项目名，不敏感；
  放这里才能版本化（看得到关注怎么演变）、能 review、能随机器迁移。
- 三级：`core`（必须给结论）/ `watch`（有亮点才提）/ `observe`（只在特别相关时提）。
- 改关注 = 改这个文件走 PR。**不要**再在本地维护第二份。
- 防腐：某个 `core` 连续多日「没看到有人在做 + 我也没进展」→ 提醒降级或删除。

## 6. 通用约束

- 话题分析基于 `topic_frequency` 和 `trend_gain`，不凭感觉
- 每个判断都要能指回具体仓库
- **星多不等于无关**（反例：`morluto/rea` 31 万星，但 topics 有 `dsh-plugin`）；
  **星少也可能关键**
- MCP / CLI 只是形态，看能力本身 —— 操作者有 bash，大多数 MCP 是冗余的
- **自动化方案的稳定性优先级：API > 协议/CLI > UI 元素树 > 截图视觉**
  - GUI 方案只在对方没有 API 时才值得考虑
  - 采用 GUI 方案时要提示「对方开放 API 后应迁走」
- 之前推荐过的项目跳过
- **不要自动写飞书 Base** —— 收录必须等人确认

## 7. 周报的差异

同一套两个板块，差异在判据：

| 位置 | 日报 | 周报 |
| --- | --- | --- |
| 1.1 | `topic_frequency` + `trend_gain` | `topics_persistent` vs `topics_emerging`，看 `days_present` |
| 维度二「我的进展」 | 当日数字 | **`star_delta`（一周净增）**，不用 `peak_daily_gain`（单日易被爆点误导） |
| 板块二 | 今天这一次的观察 | **这一周的累计变化**，并对比收录时的 Stars |

周报额外要看**跨周方向性变化**：

- 某个 `core` 连续几周「没看到有人在做 + 我也没进展」→ 判断是自己太早，还是确实没需求
- 连续几周「有越来越多人在做」→ 赛道在变热，要加速或被淹没
- 连续几周「落后」→ 该补上或明确放弃
- 某个 `core` 连续 3 周以上「无人区 / 落后」→ 建议降级或从清单删除

**这类判断日报告诉不了，是周报存在的理由。**

周报前必须看聚合结果的 `trustworthy`：为 `false` 时只报「本周数据不足 N 天，
趋势判断不可靠」，**不硬做结论**。
