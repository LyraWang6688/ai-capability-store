# @lyra_wang/dsh-terminal-context

把 **DSH 侧边栏终端**当前屏幕的内容交给 Agent，让它下一步的指令依据你真实的终端状态，
而不是凭空安排。

## 它解决什么

你在侧边栏终端里跑命令时，Agent 看不到你敲了什么、看到了什么报错、在哪个目录。
于是它给的指令经常"对着空气"：让你 `cd` 到已经在的目录、重复你已经做过的步骤、
或者在你已经失败的前提下继续往下走。

装上之后，Agent 能读到当前屏幕，于是：

- 知道你**在哪个目录**（不用你说）
- 知道你**上一条命令的结果**（成功/报错）
- 你跑完之后，它能**接着结果往下做**

## 怎么工作

```
界面侧（同一页面）               Host 侧
读 .xterm-rows 渲染出的可见行  →  POST /plugins/terminal-context/push  →  内存缓存
                                                                       ↓
                                                          Agent 工具 read_terminal_context
```

**只读**：不改终端、不发输入、不落盘（终端里可能有 token，进程结束就没了）。

## 0.5.x：显式共享 + 五种信号

0.4.x 是"Agent 想看了才调工具"。0.5.x 把终端变成 Agent 的**实时上下文**，并在需要决策时**主动叫醒它**。

### ⓿ 共享开关（默认关）

输入框左侧一个按钮：`● 共享终端` / `○ 共享终端`。

- **默认不共享**，且**按会话独立**：A 会话打开共享不会让 B 会话也在共享状态
- 偏好存在 `localStorage`（`dsh-terminal-context:share:<sessionId>`）
- 关掉 = 彻底静默：不读屏、不推送、Host 清空该会话的屏幕、取消所有计时器；`read_terminal_context` 返回 `sharing switched off`
- 对齐「共享」的直觉：我点共享它才看，我点停止它立刻不看

### ① 每一步都在上下文里（对应"第一条指令要适配当前状态"）

（仅在共享开启后生效）

Host 半边注册一个动态运行时上下文（`systemPrompt.context`），**每个模型 step 组装 prompt 时重新求值**：

- 内容：终端最后 20 行 + 多少秒前更新
- 会话对齐：界面侧从输入框 slot 的 props 拿到 `sessionId` 一起推上来，Host 按会话分桶；拿不到 `sessionId` 时退化为"用最近一次推送"
- 过期不注入：超过 45 秒没新推送就整段消失（旧屏幕比没有更危险）
- 内容没变不重复：DSH 会对运行时上下文做 diff，不变的快照不会重复消耗 token

效果：Agent 在给第一条命令前，就能看到你**当前在哪个目录、是在本地还是远端、上一条命令的结果**，不用你复述。

### ⓪ 终端没打开时：停下，让人去开（契约）

**打开终端永远由人做，插件不代劳。** 实测过两条自动化路线都不可行（`openRightbar` 只展开空壳；`remote.terminal.create` 能建出 PTY 但右栏不显示），详见「已知限制」。

所以分工固定成这样：

| 谁 | 负责什么 |
|---|---|
| **人** | 点开右侧边栏终端（新会话首次需要；之后 DSH 会记住） |
| **插件** | 每次推送都上报「面板是否打开」；没打开时在运行时上下文里写死：没有终端状态可读 |
| **AI** | 看到「面板没打开」就必须停下、请你打开，**不许**编造 cwd / 本地还是远端 / 上一条命令结果；终端一出现（约 2 秒内）自动继续 |

对应工具 `read_terminal_context` 在面板未开时返回：

```json
{ "available": false, "sharing": true, "panelOpen": false,
  "reason": "sharing is on, but no terminal panel is open; ask the user to open the right sidebar terminal" }
```

### ② 三种会唤醒的信号，各自的文案和"该做什么"

屏幕静默 1.2 秒后分类，每种信号的上报文案与要求都不同：

| 信号 | 识别依据 | 要求模型做什么 | 是否唤醒 |
|---|---|---|---|
| `error` | `error` / `npm ERR!` / `Traceback` / `command not found` / `EACCES` / `✗` 等 | 判断是否真失败；失败则只重发**从失败点开始的剩余步骤** | ✅ |
| `awaiting-input` | 末行像 `(y/n)` / `Password:` / `Are you sure?` / `Press any key` | 告诉用户该填什么，能直接粘贴的单独给出来 | ✅ |
| `interactive` | 末行不是提示符，且屏幕上有 `vim` / `less` / `ssh` / `python` / `REPL` 特征 | 别按普通 shell 给命令，告诉用户怎么退出或怎么在这程序里操作 | ✅ |
| ~~`stuck`~~ | ~~30 秒无变化，且提示符没回来~~ | **已停用**：真机上「长输出结束后的静默」和「打开面板时的空屏」都会被误判成卡住，误报比价值大 | ❌ |
| `success` | 提示符返回且无报错 | 确认结果、给下一步；不要重复已完成的步骤 | ❌ **只更新上下文** |

`success` 刻意不唤醒：批量执行顺利时保持安静——这是"理想情况别打断我"的底线。

唤醒时：

- Agent **空闲** → `followup()` 唤醒，开一个新 turn 让它处理
- Agent **正在忙** → `inject()` 不唤醒，把报告塞进下一个 step
- **一条命令最多报一次**（按「命令行文本 + 信号 + 证据」去重）；20 秒冷却
- 插件刚加载时的首屏里已有的报错**不报**（那不是这次执行产生的）

上报的消息明确写着"这是自动上报、不是用户输入"，并要求模型：判断是否真失败 → 只重发**从失败点开始的剩余步骤**，已成功的不要重跑。

> ⚠️ 这是**启发式**判定，不是退出码。屏幕上看不出 `$?`，所以：日志里出现 `error` 但命令正常结束、或 `grep error` 这类命令，都可能误触发。要精确判定失败，必须从 shell 的 `precmd` 拿 `$?`（本插件不装 shell 钩子）。

## 安装

需要 **DSH 桌面端**。

```bash
dsh plugin --profile <profile> add @lyra_wang/dsh-terminal-context
```

也可以在 DSH 的「设置 → 插件」里按包名安装。装完**重启 DSH** 生效；
侧边栏打开过终端之后，Agent 就能读到当前屏幕（工具名 `read_terminal_context`）。

> 刚 `npm publish` 之后 registry 有几分钟 staging 窗口，此时安装会 404，等一下再试。

## 不覆盖：右侧「浏览器 tab」（结构上做不到）

**本插件只读侧边栏终端，不读右侧浏览器 tab。** 这不是没做，是这条路从根上不成立。

浏览器 tab 由官方包 `@deepseek-ai/dsh-client-ui-sidebar-browser` 渲染，它的 README 写明：

> Web 使用 **iframe** 和应用维护的 history；Desktop 使用 **Electron `<webview>`**……
> 本包**不会向被访问内容注入 Electron 或 Node 能力**。

所以它和终端是两种东西：

| 面板 | 结构 | 父页面能读 DOM / 收选中吗 |
|---|---|---|
| 侧边栏终端 | 同一 document 里的 xterm DOM（`.xterm-rows`） | ✅ 能 |
| 浏览器 tab | iframe（Web）/ `<webview>`（Desktop），**独立浏览上下文** | ❌ 进不去，也收不到 `selectionchange` |

**实测（0.4.0 诊断，2026-10-26）**：全页面按 `sidebar / rightbar / panel / terminal / browser`
扫容器，只命中 1 个 `PIRFFq_sidebarCol`（左栏会话列表：「新会话 / 插件 / 自动化任务 / 工作区 /
workplace…」），浏览器 tab 正文 **0 命中**。桌面版和 Web 版都一样，因为两者都不是同一 document。

想拿浏览器里的内容，只有这三条路（代价递增）：

1. **只拿 URL + 标题**（面板自己保留），正文由 Agent 按需抓（公开页 `web_fetch`，需登录态用浏览器 MCP）
2. **自建同源代理**：Host 路由把页面取回来再渲染，同源才有机会读 DOM；要处理相对链接、CSP、登录态
3. **在用户自己的浏览器里装扩展/userscript**，把选中内容主动推给 Host 路由

> 结论：不要在 `querySelectorAll` 里加 `[class*="browser"]` 之类的选择器试图修——那修不好。

## 已知限制

- **只能读到当前可见的一屏**（最多 60 行）。向上滚出屏幕的缓冲读不到 —— 这是"看屏幕"这条路的固有代价。
- 依赖 xterm 的 DOM 类名（`.xterm-rows`）。xterm 大改版会失效，失效表现是"没数据"，不会影响 DSH 启动。
- 内容**变了才推**，每 2 秒检查一次。
- **报错判定是启发式**：没有退出码，只有屏幕文字特征（见上）。误触发时模型会多消耗一个 turn，不会做危险操作。
- **只在 DSH 右侧边栏终端生效**。iTerm / 系统 Terminal 里的命令不在覆盖范围。
- 终端里的敏感内容（token、密码提示、内部报错）会随上下文注入进入模型请求与会话日志，不再是"只有调工具才读"——所以默认**不共享**。
- `success` / `stuck` 的判定依赖提示符形状（`%` `$` `#` `❯` `➜` `»`）。自定义提示符结尾不是这些字符时，这两类信号会失效（`error` / `awaiting-input` 不受影响）。

## 安全设计

`inject: []` —— 界面插件不声明任何服务依赖。这是刻意的：DSH 的界面插件如果声明了一个
不存在的服务，入口会永久 pending，**导致整个界面起不来**（v0.1.0 踩过这个坑）。
不声明依赖，最坏情况是"插件没反应"，不会拖垮应用。

Host 半边的 `systemPrompt` / `agents` 服务用 `ctx.get()` **可选访问**，缺失时自动降级为 0.4.x 行为
（只有 `read_terminal_context` 工具，不注入、不唤醒），不会让插件起不来。

内存里的屏幕缓存不落盘，进程结束即消失；但注入进上下文的内容会随会话持久化。
