# wechat-draft-mcp · 开发思路与工程方法论

> 给"另一个 AI"阅读：这个项目从"个人痛点"做到"任何宿主都能调用的能力"，中间遵循了哪些原则、踩了哪些坑。
> 代码规模：`src` 1,439 行 / `tests` 2,580 行（测试比源码多，是刻意的）；29 个跟踪文件；112 项测试 / 19 套。

---

## 0. 一句话定义

**把磁盘上的一个文章文件夹，变成微信公众号草稿 —— 只创建草稿，绝不发布、绝不群发、绝不删除。**

这个定义里的后半句（"绝不做什么"）和前半句一样重要。见 §1。

---

## 1. 第一步不是写功能，是把"边界"钉死

绝大多数工程事故来自"以为不会发生的事"。所以先写**不可做清单**，再写功能：

| 不变量 | 为什么 | 怎么保证 |
|---|---|---|
| 只创建草稿，不发布/不群发/不删除 | 发布是不可逆的对外动作，错了收不回来 | 代码里根本没有发布接口；能力上架时明确规定 |
| stdout 只输出 JSON-RPC | MCP stdio 的协议通道；混入一行日志宿主就"显示已连接但零工具" | `console.log` 重定向到 stderr；测试逐行断言 stdout 全是合法 JSON-RPC |
| 凭证只由宿主注入（环境变量），程序不读 `.env` | 避免密钥落盘/进版本库 | `readCredentialsFromEnv()`；`.env*` 全部 gitignore |
| 错误信息不回显密钥 | 日志/报错会被复制粘贴到各处 | 统一脱敏后再抛出 |

**原则**：边界不是文档里的一句话，而是**代码结构 + 一条测试**。每条不变量都要有对应的断言。

## 2. 架构：一套核心 + 多个壳

```
                  核心（Core）
   读文章包 → 预检 → 传图 → 建草稿 → 幂等去重 → 读回核验
   src/articleBundle.ts  publish.ts  wechatApi.ts  security.ts  deliveryState.ts
                              │
        ┌─────────────────────┼─────────────────────┐
        ▼                     ▼                     ▼
   MCP 壳（stdio）        CLI 壳               Skill（提示词层）
   给豆包/WorkBuddy 用    给自己/自动化/其他 AI   告诉宿主 AI「何时用、怎么用」
   src/mcpServer.ts       src/cli.ts           skills/wechat-draft/SKILL.md
```

**为什么这么分**：

- 能力**不属于任何宿主**。同一份代码，豆包可以调、WorkBuddy 可以调、一个 CLI 可以调、另一个 AI 可以直接 `publishArticleBundle()` 调用、npm 装完任何人都能跑。
- 壳只做"翻译"：MCP 壳把工具调用翻译成核心函数；CLI 壳把命令行翻译成核心函数。**壳里没有业务逻辑**，所以加一个壳不碰核心、不改测试。
- 这是"应用商店 vs 车间"的差别：能力是资产（在你的磁盘/包里），宿主只是入口。

## 3. 不可逆操作的三条铁律

凡是要"往外部世界写东西"的功能，都要同时满足这三条（本项目三条都在 `src/deliveryState.ts` + `src/publish.ts`）：

### 铁律一：先落盘，再动手

在**第一次调用外部接口之前**，先把状态写成 `creating` 落盘。

- 若之后成功 → 更新为 `created` + `mediaId`
- 若中途崩溃 → 磁盘上留下 `creating`：**人知道"可能已经建了草稿"，去后台看一眼即可**，程序不会盲目重试

原则：**宁可留下"可能发生"的痕迹，也不要留下"不知道有没有发生"的空白。**

### 铁律二：内容指纹幂等

`bundleHash = sha256(正文 + 元数据 + 封面 + 正文图)`。

- 同一份内容第二次调用 → 返回**既有草稿**，不重复创建
- 内容变了（哪怕只换封面）→ 指纹变化 → 自然创建新草稿

**幂等是给"重试"用的安全网**，所以不要为了"想再建一条"去加 `--force`（那会拆掉安全网）。真实需求几乎都是"内容变了再建一条"，而那本来就会自然发生。

### 铁律三：单飞锁

同一个文章包并发调用时，用文件锁串行化（`.lock`），避免两条流程同时跑到"创建草稿"。

**这三条与具体业务无关**，可以原样搬到任何"会写外部系统"的项目里。

## 4. 安全：路径与凭证

- **凭证**：只从环境变量取；启动时归一化 + `trim`（真实世界有人会带空格粘贴）
- **路径逃逸**：所有读文件都走 `resolveInsideBundle()` —— 先 `realpath` 解析，再断言目标在文章包目录内
- **禁止前缀**：`/etc`、`/private/etc`、`~/.ssh` 等
- **错误脱敏**：微信返回的 `errcode/errmsg` 保留，但 `access_token`、`appSecret` 一律替换

### 测试挖出来的 5 个真实缺陷（这是"为什么要写测试"的最好论据）

| 缺陷 | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 能从 `/etc` 读到东西 | macOS 上 `/etc` 实际是 `/private/etc` 的软链，前缀黑名单只写了 `/etc` | 加上 `/private/etc`；**对路径先 realpath 再判断** |
| 2 | 符号链接可逃出文章包 | 只检查了原始路径拼串，没解析真实路径 | `resolveInsideBundle` 用 realpath 做包含性检查 |
| 3 | 把 `data-src` 当正文图处理 | 正则 `\bsrc` 会匹配到 `data-src` 里的 `src` | 改成 `(?:^\|\s)src` —— 要求 src 前是空白或行首 |
| 4 | 作者来源判断恒为假 | 用 `!values.author` 判断"未从 meta 取到"，但空串/undefined 语义混淆 | 显式区分"未提供"与"空值" |
| 5 | 摘要被截断提示覆盖 | 后写的字段覆盖了前一步的告警 | 改为累加式 warnings，不覆盖 |

**共性**：五个都不是"业务逻辑写错"，而是**边界情况**（软链、正则词边界、类型语义、覆盖顺序）。这类 bug 只能靠"对着边界写测试"发现。

## 5. 测试策略：分三层，且不依赖生产开关

| 层 | 测什么 | 例子 |
|---|---|---|
| **单元/解析层** | 纯函数、HTML/meta 解析、路径安全、状态机 | `articleBundle.test.ts`、`security.test.ts`、`deliveryState.test.ts` |
| **通道层 e2e** | 真正走一遍 MCP 协议 + 完整上传 | `mcpStdio.test.ts`（握手 + `tools/list`）、`mcpUploadE2E.test.ts` |
| **契约层** | 打包产物本身的契约 | `packageContract.test.ts`（`bin`/`files`/`exports`/版本一致性） |

### 两个关键设计决定

1. **通道层 e2e 不依赖生产环境的开关。**
   做法：用 `node --import <interceptor>` 在**进程启动时**劫持 `fetch`，把 `api.weixin.qq.com` 的请求改写到一个本地 mock 服务器。
   好处：生产代码里**没有** "测试模式"分支（不需要 `if (process.env.TEST)` 这种可被误触发的开关），而测试仍然跑完整链路。

2. **打包产物要单独测。**
   `packageContract.test.ts` 断言：`bin` 指向的文件存在、`files` 白名单包含 `dist`、`exports` 的子路径可解析、`package.json` 的版本与握手报告的版本一致。
   价值：**避免"本地能跑、装完不能跑"**（真实发生过：`.gitignore` 会被 npm 当成忽略来源，如果不显式写 `files`，`dist/` 会被排除）。

## 6. 分发：从"我能跑"到"谁都能跑"

### npm 打包的四个硬要求

1. `bin` 指向 `./dist/mcpServer.js`（并加 shebang）
2. **显式 `files` 白名单** —— 不写的话，npm 会回落到 `.gitignore`，把 `dist/` 一起排除
3. `prepare` 脚本负责发布前构建（`npm publish` 会自动跑）
4. `exports` 暴露子路径（`./publish`、`./articleBundle`、`./wechatApi`），让别人能按模块引用

再加一个 `check:pack` 脚本：`typecheck && test && npm pack --dry-run`。

### 核验"分发产物"，而不是"本地代码"

发布前逐项核验**将被发布的东西**：

- 包内容清单：11 个文件、23.3 kB
- 无密钥痕迹（正则扫 `appsecret`/`wx…`/`sk-`/`BEGIN`）
- 无测试、无 `.env`、无 `HANDOFF.md`、无 `node_modules`
- 发布后**从公共源装一份**到临时目录，真跑一次握手（`serverInfo.version` 正确 + 4 个工具 + stdout 纯净）

**原则：永远不信"本地 tarball"，要验"从公共源装下来的那一份"。**

## 7. 与平台/仓库协作的铁律（血泪）

| 铁律 | 为什么 |
|---|---|
| **`git subtree` 的合并提交绝不能 `--amend`** | `git subtree pull` 靠提交信息里的 `git-subtree-dir:` / `git-subtree-split:` trailer 找锚点；amend 会把 trailer 丢掉，之后每次 pull 都冲突 |
| **subtree 类 PR 必须用 merge commit 合并** | squash/rebase 会让锚点提交不再是 main 的祖先，锚点断裂 |
| **一个仓库一个事实源** | 版本号只写在能力注册表里，测试数量只以 `npm test` 输出为准；文档里不硬编码会漂移的数字 |
| **交接文档不进版本库** | 会话状态（ID、进度、临时决定）会随时间漂移；一旦进库并被镜像到多处，就得逐处收敛。让它只在本机 |
| **写操作前先只读预检** | `inspect` 先跑一遍（不调用外部），`ready: true` 再执行 |
| **沙箱越界要"最小提权"** | 写工作区之外的幂等账本会被拦 —— 正确做法是**申请最小必要权限并说明理由**，不是绕过 |

## 8. 值得复用的工作流：预检 → 落盘 → 执行 → 读回核验

本项目每一次"往外部写"的动作都走这四步：

```
① 只读预检（不碰外部）：字段齐不齐、超限没有、图片能不能读
② 落盘（本地状态机）：creating
③ 执行（外部）：上传图片 → 建草稿
④ 读回核验（再从外部读一遍）：标题对不对、图片是不是已换成平台地址、占位符有没有残留
```

第 ④ 步最容易被省略，但它才是"交付"与"我提交了"的分界线。**能读回验证的结果，才叫完成。**

## 9. 踩过的坑（现象 → 根因 → 预防）

| # | 现象 | 根因 | 预防 |
|---|---|---|---|
| 1 | `node --test dist-test/tests/` 在 Node 24 报 `Cannot find module` | 该版本不支持目录参数 | 用 glob：`node --test "dist-test/tests/**/*.test.js"` |
| 2 | macOS 临时目录断言失败 | `/var` 与 `/private/var` 是同一个地方的两个名字 | 断言前先 `realpath` |
| 3 | 包发不出去 | `package.json` 里残留 `private: true` | 发布前 `check:pack` 校验 |
| 4 | 装完不能用 | `files` 没写 → npm 回落到 `.gitignore` → `dist/` 被排除 | 显式白名单 + 契约测试 |
| 5 | `git subtree pull` 每次都冲突 | 早先对锚点提交做过 `--amend`，trailer 丢了 | 锚点提交永不 amend；PR 用 merge commit |
| 6 | npm 命令报权限错误 | 全局缓存目录归属不对 | 指定可写缓存目录；不要动系统目录 |
| 7 | 越界写被沙箱拒绝 | 写工作区之外的目录 | 申请最小权限并说明用途，不用绕过手段 |

## 10. 把"踩坑"变成资产

本项目把错误分成两类，区别对待：

- **产品缺陷**（§4 那 5 个）→ 修代码 + 补一条回归测试，让它永远不再出现
- **流程错误**（§7、§9）→ 写进文档/技能（比如"subtree 提交永不 amend"），变成别人不用再踩的知识

**一个团队/一个人的工程水平，很大程度体现在"错误会不会重复出现"。**

## 11. 复用到下一个项目的检查清单

```
□ 先写"绝不做什么"，并为每条不变量配一条测试
□ 拆成"一套核心 + 多个壳"，壳里不放业务逻辑
□ 凡是写外部的功能：先落盘 → 幂等指纹 → 单飞锁
□ 边界情况（软链/正则边界/空值语义/覆盖顺序）优先写测试
□ 端到端测试不引入生产开关，用进程级拦截/mock
□ 分发前核验"产物本身"，并从公共源装回来真跑一次
□ 指定单一事实源（版本看注册表、测试数看命令输出），文档不写会漂移的数字
□ 把"预检 → 落盘 → 执行 → 读回核验"固化成流程
□ 每次犯错都问：这是产品缺陷还是流程缺陷？前者写测试，后者写文档
```

## 12. 破坏性操作怎么加才不失控（0.3.0 的案例）

需求是"要能更新和删除"，而删除是**不可逆**的。这类需求最容易把前期积累的安全边界一次性毁掉。
0.3.0 的做法：**先把风险结构化，再写代码**。

| 门 | 机制 | 为什么 |
|---|---|---|
| ① 开关 | `WECHAT_ALLOW_DESTRUCTIVE=1`，**默认关闭** | 让"能删"变成一次刻意的启用，而不是默认就躺着的能力。任何误调用/提示词注入都不能直接删线上内容 |
| ② 目标确认 | `confirm` 必须等于目标 ID 的后 6 位 | 强制调用方真正"看过目标"。防止"删最近一条"这类模糊指令被翻译成破坏性动作 |
| ③ 先备份 | 删除/更新前把目标内容落盘到 `state/backups/` | 不可逆动作也要留下可重建的原料。备份失败即中止，绝不"没备份就删" |
| ④ 审计 | 每次操作写 `state/audit.jsonl`（时间/操作/目标/结果/备份路径） | 事后可追溯；失败也要记录 |

配套的两个设计决定：

- **`draft/update` 不受①②约束**（它不改变"存在性"），但**照旧先备份** —— 因为它会覆盖用户可能在编辑器里手工改过的正文。
- **账本（幂等账本）要跟着失效**：草稿被更新后，旧内容指纹指向的条目必须标记 `supersededAt`；
  草稿被删除后必须标记 `deletedAt`。否则下次上传同内容会"复用"到一个内容已变、甚至已经不存在的草稿。
  **不可逆操作的影响面不止在外部，还在自己的状态文件里。**

原则一句话：**越危险的动作，越要把"它怎么被触发、怎么被确认、怎么被还原、怎么被追溯"写成代码，而不是写成叮嘱。**
