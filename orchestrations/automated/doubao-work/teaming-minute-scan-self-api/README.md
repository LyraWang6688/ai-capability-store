# teaming-minute-scan-self-api（-self-api：调自建 API）

**宿主的定时任务醒来 → 查最近 N 小时的新妙记 → 逐场判断 → 只分析相关的 → 汇报（含跳过清单）。**

这是 teaming 的**主要用法**（`trigger: host-schedule`）；`teaming-meeting-review-self-api` 是同一
skill 的单场变体（人问一场会）。两者共用一个后端服务，但输入、产出和失败方式不同，
所以是两条编排。

```text
1-scan  → skills/teaming-meeting-analysis
          └── calls: meeting-analysis-service
```

---

## 三段

| 段 | 谁做 | 具体 |
|---|---|---|
| ① 取数 | 宿主自己的飞书能力 | 查最近 N 小时**你自己**的新妙记，按 token 去重，只留新出现的 |
| ② 逐场判断 | 宿主（模型） | 每场先看标题 + 稿子开头；明显无关的**不上传** |
| ③ 调用 | 宿主 shell + 服务 | 相关的逐场 `POST /api/host/v1/analyze`（`--max-time 150`，带 `feishuMeetingId`） |
| ④ 汇报 | 宿主 | 每场的结论 + `reportUrl`；**跳过的要列出来**；一场都没有就如实说 |

## 衔接规则（不属于任何一方，所以只能写在这里）

1. **定时时没人可问，所以规则更硬。** 逐字稿一旦 POST 出去就出本机，没人能替用户决定。明显无关的（纯技术排障、内部行政、产品例会、闲聊、单人录音）→ 跳过、不上传，并在汇报里列一行「这场会不在范围内，已跳过」。
2. **跳过清单是交付物的一部分。** 用户看到汇报要能问「这场为什么没分析」——所以「跳过」不能只是日志。
3. **查询为空就如实说明。** 不要编造数据，也不要为了有输出而分析一场无关的会。
4. **按 token 去重，只处理新出现的。** 与上次已处理过的比对；重复处理同一场会会命中服务端幂等（不重复消耗额度），但仍然不该重复汇报。
5. **单场超时不等于失败。** 重试是安全的（幂等命中）；`not_abc_related` 不要重试。

## 前提

- 宿主能执行（`bash` + `curl`），并出网到 `meeting.bamamei.online`
- 宿主具备飞书能力（查妙记、导出逐字稿）
- 一个 host token（8 位接入码兑换，存 `~/.teaming-mcp/host-token`，600）；第一次定时跑时如果没有，要先走「准备」三步拿到

## 不做的事

- 不做会议摘要 / 待办
- 不评价个人
- 不负责"什么时候跑"：钟是宿主的定时任务，不是 `automations/` 里的 automation；具体任务配置在归属人的宿主里
- 不复制分析逻辑 —— 服务在独立仓库 `teaming-bot`
