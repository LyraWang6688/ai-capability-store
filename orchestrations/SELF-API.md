# SELF-API —— 调自建后端 API 的编排，接口写在 SOP 里

## 一句话

> **宿主按 skill 里写死的契约调一个自建的后端服务。**
> 算力与规则在服务端，宿主只负责取数、出网、交付。

这不是一个【模式】，所以它不回答"谁发起"：可以是人触发的（teaming），也可以是
自动化叫醒的（readloop）。标志只有两个：**任务目录名带 `-self-api`**，且 **step 里有 `calls`**。

---

## 三段的形状

| 段 | 回答什么 | 典型形状 |
|---|---|---|
| **① 取数** | 数据从哪来 | 宿主自己的飞书能力 / 宿主插件 / 搜索 |
| **② 调用** | 谁算、谁判 | `curl` 打店外服务；Bearer host token；幂等键由宿主给 |
| **③ 落回** | 用户在哪看到 | 写回用户自己的表 / 报告链接 / 卡片 / 对话 |

`manual` 和 `automated` 两种触发方式里都可能有调自建 API 的任务；判断它属于哪种看
`trigger`，判断它是否调自建 API 看任务目录名和 `calls`。

---

## 前提是"宿主的执行能力"，不是"装了某个资产"

```text
manual / automated：  能力边界 = 已登记资产的集合       （装什么，会什么）
-self-api：          能力边界 = 宿主的 shell + 网络    （会 curl 才有这一段）
```

所以 `execution.requires` 必须声明 `bash` / `curl` / `network` 这类**能力项**。
换宿主时，能不能跑这条编排，查这个字段就知道 —— 不需要去读 skill 正文。

---

## 边界规则（这一类最容易安静坏掉的地方）

1. **数据出机是决策点**：能本地判断的先判断，只传必需的字段。
2. **结果权威在服务端**：判分 / 报告 / 间隔不能由 agent 重算。
3. **幂等键由宿主提供**：否则重试 = 重复计费 / 重复建行。
4. **凭证在用户机器**：接入码 → host token，存 `~/.<product>/`（600），店里零 token。
5. **失败分支写进契约**：401 / 402 / 5xx / 超时各自的动作是固定的。
6. **契约只有一份**：`calls.contract` 必须等于服务记录的 `contract_path`。

---

## 不算这类编排的

| 情况 | 为什么不算 | 在哪 |
|---|---|---|
| 调公开平台 API（GitHub / 飞书 OpenAPI） | endpoint 是别人的，契约不是产品的 | 普通 skill 的确定性脚本 / 宿主能力 |
| 数据来自宿主的搜索或插件 | skill 里零 endpoint，没有"接口"这回事 | 能力调用 |
| 店里托管的 MCP / CLI 客户端 | 调用被资产承载了，用 `use` 引用即可 | `external-capabilities/` |

判据三条，缺一不算：**endpoint 写在 skill 里** + **后面是自建后端** + **契约在 skill 的 `references/` 里**。
