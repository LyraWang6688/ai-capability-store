# 微信公众号草稿上传

把用户已经准备好的一篇文章，创建成微信公众号草稿。

**默认只创建草稿。** 0.3.0 起支持原地更新草稿，以及在显式开启后删除草稿/素材/已发布文章；这些操作改前自动备份、改后写审计。**正式发布始终由用户在公众号后台人工完成。**

本技能依靠 `wechat-draft` 连接器（本地 stdio MCP），它提供 4 个工具：

| 工具 | 用途 | 副作用 |
|---|---|---|
| `wechat_draft_status` | 体检：凭证、出口 IP 白名单、草稿箱权限 | 无 |
| `inspect_wechat_article` | 上传前预检文章文件夹 | 无 |
| `upload_wechat_draft` | 创建草稿 | 有（仅草稿） |
| `get_wechat_draft` | 按 `media_id` 读回草稿核对 | 无 |

---

## 一、什么时候用

用户表达了明确的**上传意图**：

- 「把这篇文章传到公众号草稿箱」
- 「帮我上传到我的公众号」
- 「放进草稿箱」
- 「这个发到公众号上去」

### 什么时候**不要**用

| 用户说什么 | 该做什么 |
|---|---|
| 「帮我写一篇文章」 | 只写。**不要**调用上传工具 |
| 「你觉得这篇写得怎么样」 | 只给意见 |
| 「把这篇文章发出去」 | 先确认：是**草稿箱**还是**正式发布**？正式发布本工具做不到，必须用户在后台手动完成 |
| 用户还没确认文章内容 | 先给用户过一遍，等他明确说上传 |

**判断标准：用户没说「上传 / 传 / 放进草稿箱」，就不要调用 `upload_wechat_draft`。**

---

## 二、最关键的一条：文章必须先在磁盘上

上传工具**只接收文件路径**，正文内容不经过对话。这样做的好处是 token 消耗与文章长度无关。

所以如果文章是**你在对话里生成的**，你必须先把它写到磁盘：

```
1. 建一个文章文件夹（放用户容易找到的位置，例如 ~/Documents/公众号文章/<日期>-<标题短名>/）
2. 写入 article.html     ← 正文
3. 写入 metadata.json    ← 标题/作者/摘要
4. 放入 cover.png        ← 封面（必需）
5. （可选）images/       ← 正文插图
6. 然后才调用 inspect_wechat_article(bundle_path=该文件夹的绝对路径)
```

**绝不要把整篇 HTML 塞进工具参数。** 参数里只有路径。

## 三、文章文件夹的结构

```
我的文章/
├── article.html       正文（必需）
├── metadata.json      元数据（强烈建议）
├── cover.png          封面（必需）
└── images/            正文插图（可选）
    ├── fig1.png
    └── fig2.jpg
```

### metadata.json

```json
{
  "title": "文章标题",
  "author": "作者名",
  "digest": "摘要，最多 120 字"
}
```

字段都可以省略，省略时会尝试从 HTML 的 `<h1>` / `<title>` / `<meta>` 里提取。

### article.html 的要求

| 要求 | 说明 |
|---|---|
| 图片用**相对路径** | `src="images/fig1.png"`。工具会自动上传到微信并替换成微信图片地址 |
| **不要用外链图片** | `src="https://图床/xx.jpg"` 会被微信过滤掉，草稿里会裂图 |
| **不要用 data: URI** | 微信素材接口不接受 base64 |
| 样式写在标签上 | 用 `style="..."` 内联样式，微信不支持 `<style>` 标签和 class |
| 完整文档或片段都行 | 工具会自动剥掉 `<!DOCTYPE>` / `<html>` / `<head>` / `<body>` |
| 图片格式 | 只支持 jpg / png，单张 **小于 1MB** |
| 正文长度 | **少于 20000 字符** |

### 封面

微信**强制要求**封面。命名成 `cover.png` / `cover.jpg` 放在文章文件夹里，工具会自动找到。
尺寸建议 900×383 或 2.35:1，否则微信会自动裁剪。

## 四、标准流程

```
用户说要上传
    ↓
① wechat_draft_status          ← 先确认环境正常（可选，但上传失败时必做）
    ↓
② inspect_wechat_article       ← 预检：能不能找到正文和封面、有没有阻塞问题
    ↓
   blockingIssues 非空？
    ├─ 是 → 把问题如实告诉用户，**不要上传**，等他修好
    └─ 否 ↓
③ upload_wechat_draft          ← 真正上传
    ↓
④ 把结果告诉用户
```

### 上传成功后怎么回复用户

**不要说**「草稿 media_id 是 AX7Qh8wE...」——用户看不懂。

**要说**：

> 已经帮你上传到微信公众号草稿箱了，标题是《XXX》。你有空去公众号后台的草稿箱看一下排版，确认没问题再手动发布。

如果 `warnings` 非空，把警告也翻译成人话告诉用户（例如「正文里有 3 张外链图片，微信可能会过滤掉，建议改成本地图片」）。

## 五、错误怎么处理

| 工具返回 | 你要做什么 |
|---|---|
| 提示 **IP 不在白名单** | 告诉用户：把返回里的那个 IP 加到 公众号后台 → 设置与开发 → 基本配置 → IP白名单。**换 Wi-Fi 或开 VPN 后 IP 会变，需要重新加** |
| 提示 **凭证未被注入** | 告诉用户去连接器配置页重新填 AppID/AppSecret 并保存，然后重连 |
| 提示 **结果未知 / 上一次上传未完成** | ⚠️ **绝对不要重试**。告诉用户：先去草稿箱看看是不是已经建好了，确认后再处理 |
| 用户让你核对某次上传、或手里有 `media_id` | 用 `get_wechat_draft` 读回草稿，比对标题。**不要凭记忆或猜测回答「应该传上去了」** |
| `blockingIssues` 非空 | 逐条翻译给用户，让他补（通常是缺封面、正文太长） |
| **调用超时** | ⚠️ **不要自动重试**。先说「上传结果不确定，请先到草稿箱确认」，再按用户指示行动 |

### 重复上传是安全的

同一篇文章（内容没变）再调用一次 `upload_wechat_draft`，会返回**已有的草稿**，不会重复创建。
返回值里 `reused: true` 就表示这次是复用。回复用户时说「这篇之前已经传过了，还是同一条草稿」即可。

（如果用户改了文章内容，会产生新草稿——这是预期行为。）

---

## 六、绝对不要做的事

- ❌ 用户只是让你写文章，你就去上传
- ❌ 用户说「发布」，你当成「上传草稿」（**发布本工具做不到**）
- ❌ 上传失败就反复重试（可能造成多条重复草稿）
- ❌ 把完整 HTML 放进工具参数（应该写文件、传路径）
- ❌ 把 AppSecret、access_token 打进对话里
- ❌ 在没有用户明确要求的情况下，自己决定把哪篇文章传上去
