# 交付格式与调用方式

## 创作

默认交付可直接使用的标题与正文；摘要、备选标题和配图建议按媒介或用户需要提供。内部完成规则检查，除非用户要求或存在实质待确认项，不附冗长审阅表。

事实不足时，可以基于已知材料完成可确定部分，再列最少的待确认项。不要用模板化的个人感受填空，不把例子包装成用户经历。

## 审阅

先回答内容基础如何，再列真正影响结果的问题，必要时附重点段落改写：

- **判断与范围**：读了什么、只做内容检查还是另有线上验证。
- **有依据的优点和问题**：位置、影响、修改建议；没有实质问题就直接说明。
- **待验证项**：只列与任务有关的事实或平台状态，不把所有未知列成缺陷。

需要完整报告时，可按“维度｜状态｜原文依据｜建议”整理，不强制每个维度都有问题。

## 修订

交付完整最新版与必要的变更说明，不只交建议。用户已授权修改本地文件时，更新对应正文；已授权且存在 HTML 或摘要时，同步保持版本一致。新增事实必须核验或标为待确认，保持原有真实进度边界。

公开正文与内部核验记录分开保存。没有要求文件就直接在会话交付，不强制创建目录、数据库或长期状态文件。

## 可直接调用

- 用 $geo-content 审阅这篇公众号文章的主题、可摘引性和事实边界，只给有依据的问题。
- 用 $geo-content 按这些真实材料写一篇文章，解释哪些重复任务适合脚本化，保持自然叙事。
- 用 $geo-content 整合修改这份产品说明，给出完整最新版，保留适用条件。
- 用 $geo-content 复查这篇已修改文章，重点看上一轮问题是否修好，不增加没有依据的新问题。

“每次写完都检查”可在写作请求或项目流程中调用；“每周自动检查”需要另有调度和可读取的内容来源。不要从“定期使用”自行推断运行时间、批量范围、发布权限或通知对象。
