# 组队会议动力分析

对**一场已结束的会议**做团队动力分析。理论依据是 Amy Edmondson 的 Team Learning / Teaming / Psychological Safety，以及 Kantor 的互动功能模型。

**这是观察工具，不是考核工具。**

本技能依赖 `teaming-mcp` 连接器（本地 stdio MCP），它提供 6 个工具：

| 工具 | 用途 | 副作用 |
|---|---|---|
| `teaming_doctor` | 体检：飞书授权、分析凭证、引擎是否就绪 | 无 |
| `teaming_list_meetings` | 列出近期会议，并标注哪场有逐字稿 | 无 |
| `teaming_read_report` | 读某场会已生成的报告摘要 | 无 |
| `teaming_analyze_meeting` | 对一场会做分析，产出报告 | 有（落盘） |
| `teaming_job_status` | 查分析任务进度 | 无 |
| `teaming_push_report` | 把报告作为交互卡片推送到飞书 | 有（发消息，幂等） |

---

## 一、什么时候用 / 不要用

**用**：
- 「分析一下今天的产品周会」「看看这场会的团队氛围」「这次会议复盘一下」

**不要用**：
- 只要会议摘要、待办整理、纪要转写 → 用宿主自带的会议纪要能力
- 只是查会议列表、时间、参会人 → 直接回答即可
- 用户要评价某个人 → 本技能明确不支持

---

## 二、标准流程

### 第 1 步：确定是哪场会

先调 `teaming_list_meetings`。若用户没说清是哪场，列出候选让用户选，**不要自己猜**。

看 `analyzable` 字段：
- `false` → 这场会没有逐字稿，**直接告诉用户无法分析**，不要尝试用 AI 纪要替代

### 第 2 步：先查有没有现成报告

调 `teaming_read_report(meeting_id)`。若有，直接汇报，**不要重复分析**（分析要花 60~120 秒且消耗额度）。

### 第 3 步：没有报告才分析

调 `teaming_analyze_meeting(meeting_id)`。它会自动复用已有报告，不会重复消耗。

**返回 `status="running"` 时不要重试分析**——分析已经在后台跑了，重试只会再起一个。

按返回的 `job_id` 调 `teaming_job_status` 取结果。间隔大约 30 秒查一次，通常 1~3 次就有结果。

> 为什么要这样设计：单次分析要 60~120 秒，可能超过宿主的工具调用超时。
> 分析放在后台进程执行，**等待超时不会让这一分钟算力白费**，结果随时能取。
> 用户问"还要多久"时，如实说"通常一两分钟"。

### 第 4 步：呈现结果

**不要把报告全文塞进对话。** 报告已经在 `report_path` 指向的本地文件里。按下面的方式呈现：

1. 先说区域定位（一句话）
2. 再说两个维度各一句
3. 然后是最优先建议
4. 最后说"完整报告在 <report_path>"

### 第 5 步：需要时推送

用户说「把报告发我」「推送到飞书」时，调：

```
teaming_push_report(meeting_id)
```

不传 `chat_id` 就推给用户自己（连接器会自动查和他的单聊会话）。

**推送形态是交互卡片**（蓝色标题栏 + 报告摘要 + 按钮），与团队 bot 线上一致。
**推送是幂等的**：重复调用返回同一个 `message_id`，不会产生重复消息。

> 不要自己拼消息文本去发。报告的统一形态是卡片，用这个工具。

## 三、报告怎么读（重要）

报告分四部分：

| 部分 | 内容 |
|---|---|
| **Part 1 团队状态定位** | 区域 + 心理安全 + 高要求与问责，各自带证据和限制 |
| **Part 2 互动概览** | 每位成员发挥的**功能**（推动/承接/挑战/观察）+ 互动网络 |
| **Part 3 未完成的对话 & 值得被看见的非共识** | 两者不同，都允许为空 |
| **Part 4 给领导者的建议** | 只给一条最优先建议 |

**区域**由两个维度组合，不是打分：

```
心理安全较高 + 高要求较高 = 学习区      较高 + 较低 = 舒适区
心理安全较低 + 高要求较高 = 焦虑区      较低 + 较低 = 冷漠区
```

出现「**证据不足，暂不定位**」或「**可能是 X 或 Y**」**是正常结果，不是失败**。这时要如实转述，**不要为了给出确定结论而重新解读**。

---

## 四、向用户解释时的硬规则

1. **不评判人格**，不诊断团队，不把单次会议外推为长期特质。
2. **允许证据不足**。报告说"暂不定位"就照实说，不要补一个更强的结论。
3. **允许某部分为空**。没提到未完成的对话就说没有，不要编。
4. **引用必须是逐字稿里的原话**。不要改写或概括成"看起来像"的话。
5. **不使用后台术语**（psychologicalSafety / higher / lower / Zone），用"心理安全""高要求与问责""学习区"这类自然中文。
6. **不评价个人**。用户问"某某表现得怎么样"时，把话题拉回**会议过程**。

---

## 五、异常处理

| 情况 | 怎么回复 |
|---|---|
| `teaming_doctor` 报飞书未授权 | 让用户在终端执行 `lark-cli auth login --recommend` 后重试 |
| 会议 `analyzable=false` | 说明该会议没有逐字稿，AI 纪要无法替代原始发言，换一场 |
| 分析返回 `status=running` | 正常。用 `teaming_job_status` 轮询，**不要重新发起分析** |
| 分析返回 `status=failed` | 按返回的 `error` 说明原因；逐字稿缺失的换一场会 |
| 逐字稿过短 | 说明证据不足以支撑判断，可以给有限观察但不下区域结论 |
| 用户要求评价某个人 | 说明本技能只观察会议中的行为与互动，不评价个人 |

---

## 六、底线

**宁可说"证据不足"，也不要给一个看起来很完整但站不住的结论。**

这份报告是给组长或助教用来改进团队协作的。任何可能被用来评价个人的表述，都要改写成对**会议过程**的观察。
