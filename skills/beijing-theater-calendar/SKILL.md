# 京城好戏 · 北京戏曲/话剧演出日历

## 项目与数据底座

- 项目：「京城好戏」——监测北京剧场未来时段演出，服务主理人周末看戏、随时查询、决策买票。
- Base「北京剧场演出日历」token：`AFEkbH7DQaf3tfsJuL1ctwf5nWg`
  链接：https://my.feishu.cn/base/AFEkbH7DQaf3tfsJuL1ctwf5nWg
- 交接文档（完整口径，接手必读）：https://my.feishu.cn/docx/OnE6dC8fcoBgxQx8NcKcb6V6n0c
- 范围：**仅限北京**；**只收「戏曲」「话剧」两品类**（喜剧/音乐剧/儿童剧不纳入）；术语一律用「戏曲」，不用「戏剧」。

## 核心规则（违反即错误）

1. **不编造**：每条场次必须来自可追溯来源（剧场官网/公众号、票务平台、文旅周报）；无法确认的信息标「以票务为准」。
2. **去重写入**：按「剧目名称 + 演出日期」去重，不覆盖已有记录。
3. **Base 是唯一事实源**：任何回答先查 Base；发现缺口就补采；补采结果写回 Base（回答即维护）。
4. **动态字段勿手写**：星期 / 距演出天数 / 是否本周末 是公式字段，系统自动计算。
5. **表即路由**：补采按表路由——主打剧种定剧场，购票渠道/官方渠道定信源，不全网乱搜。

## 执行流程（双轨：手动触发为主，定时保底）

### 决策层 · 用户提问时（主路径）

1. **解析请求**：明确 时间段（今天/本周末/未来 N 天/具体日期）、品类（戏曲/话剧/全部）、剧场（可选）、输出（场次清单+购票信息）。
2. **检查数据**：查 Base 目标时间段是否有记录、是否新鲜（距最近一次写入 ≤ 2 天视为新鲜）。
3. **决策**：
   - 有记录且新鲜 → 直接查询（跳 5）；
   - 有记录但不新鲜 / 无记录 / 超出覆盖 → 进入执行层补采（见下）；
4. **查询**：用视图/筛选（本周末、未来30天、戏曲、话剧、按剧场、按日期）。
5. **回答**：场次清单（剧目/剧场/日期/开演时间/票价/状态）+ 购票渠道与链接；无匹配时如实说明并建议关注剧场。
6. **回写**：补采结果已入库，回答完成后 Base 即最新事实源。

### 执行层 · 补采三步（搜索标准动作）

1. **锚定时间区间**：具体日期直接用；「这周末/下周末/最近」等相对表述，先调用 get_current_time 锚定当前时间，换算成明确起止日期（如 9/12-9/13）。
2. **剧种 → 剧场 → 信源路由**：查「剧场档案」表——主打剧种含目标剧种的剧场为候选；取候选剧场的「常用购票渠道/官方渠道」作为目标信源；再叠加聚合信源（文旅周报：大戏看北京/文旅北京/北京日报「一周演出预告」）兜底。
3. **抓取与拓展**：在目标信源中搜「时间区间 × 剧场」的演出；拿到基础信息后拓展剧目全称、场次（日期/时间）、票价区间、购票渠道与链接；按「剧目名称+演出日期」去重写入 Base 并标注信息来源。

### 定时保底（每周一、周四 10:30）

读交接文档 → 抓取未来 30 天新增场次 → 去重写入、过期改「已结束」→ 简报（新增/更新/结束数量）。

## 工具链

- Base 读写：`lark-cli base`（user 身份；入口先 `+url-resolve`，写前读字段结构）。
- 相对时间锚定：`get_current_time`（Asia/Shanghai）。
- 信源抓取：剧场官网/公众号、票务平台（大麦/中演票务通/购票通/人艺票务中心）、文旅周报；网页内容用浏览器或搜索工具收集。
- 名词/字典变更：先问主理人确认，改字典表并同步主表选项，不要临时造选项。
