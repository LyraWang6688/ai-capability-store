# Context Submit · 投递箱

把「观察」送进投递箱。**你不负责归类，只负责如实报告。**

> **架构位置**：本 skill 是 Agent Context Architecture 的**唯一输入口**。
> 投递箱里的条目由维护者定期提炼进 `preferences` / `memory` / `global` / `integrations` / `hooks`。

## 铁律

**投递者只报告观察，不负责归类。**

「这是偏好、规则还是事实」——这个判断连人类都要讨论四轮，**不要猜**。
`类型` 字段只是给你一个低成本的表达入口；**填错不会毁掉数据**，维护者会重新判断。

## 第一步：值不值得投？

三个问题，**全部为「是」才投**：

1. 换一个项目 / 环境还会遇到吗？
2. 不写下来，下次还会踩吗？
3. 别人看了能省时间吗？

**投递箱的价值来自筛选，不来自数量。**

## 第二步：选类型

| 类型 | 什么时候用 |
|---|---|
| `踩坑` | 被某个东西坑了，且不是自己写错代码导致的 |
| `经验` | 摸索出一条可复用的做法 |
| `集成` | 关于第三方系统（API / CLI / SDK / MCP）的运作方式或陷阱 |
| `偏好` | 用户明确表达了好恶、习惯、合作方式 |
| `事实` | 需要长期记住的事实（环境、资产、历史决定） |
| `规则` | 你认为应该成为「所有项目通用规则」的东西 |

判不了就选 `经验`，维护者会重判。

## 第三步：按模板写内容

### 必填（所有投递）

```
观察：我实际看到的 / 听到的（写「我看到」，不写「我觉得」）
场景：在做什么任务、什么操作时遇到的
可复用性：换项目/换场景还成立吗？还是只对当前项目成立？
```

### 技术类补充（`踩坑` / `经验` / `集成`）

```
现象：发生了什么（有报错就贴原文，不要转述）
原因：定位到的根因 —— 不知道就写「未定位」，不许编
修法：怎么解决的 —— 没解决就写「待解决」
```

### 认知类补充（`偏好` / `事实` / `规则`）

```
原话：用户的原话（★ 不得改写，一个字都不要动）
我的解读：我认为这意味着什么（★ 明确标注这是解读，不是事实）
```

**★ 这两条是整个模板的骨头：**

- **原话不得改写** → 它是证据层，改写一次就永久失真
- **解读必须标明是解读** → 你的解读很可能错，但你的观察通常对。
  分开写，维护者才能「只采信观察、重新解读」。

## 第四步：门禁 → 查重 → 写入

### ① 门禁（必过，FAIL 不许写）

把内容写成 JSON（形如 `{"类型":"集成","内容":"...","来源项目":"...","来源会话":"..."}`），然后：

```bash
python3 scripts/validate_entry.py entry.json
```

报错就按报错改，**不要绕过检查**。

### ② 查重（建议跑）

```bash
python3 scripts/check_similar.py entry.json
```

**有相似条目照样写**——重复本身是「这是共性」的证据。
但要告诉用户「已有 N 条类似」，让他决定是否补充细节。

### ③ 写入

payload 必须是 `{"create_records":[{...}]}`，**不是裸对象**：

```bash
lark-cli base +record-batch-create \
  --base-token ZNjDb9TrpalLuCsw0macCeVdnld \
  --table-id tblPOVjILsGdG9Uw \
  --json @record.json --as user
```

### ④ 回报

写入后告诉用户：

```
已投递 #<record_id> · 类型：X · 状态：待提炼
```

**不要说成「已经沉淀了」**——它只是进了队列，还没被提炼成规则。

## 不写什么

| ❌ | 为什么 |
|---|---|
| 项目内部的一次性 bug | 那是 issue，不是可复用的坑 |
| 已经写在 `global.md` / 项目 `AGENTS.md` 里的 | 重复 |
| 纯吐槽、一次性故障 | 下次不会遇到 |
| 没验证过的推测 | 标成「解读」，或干脆不写 |
