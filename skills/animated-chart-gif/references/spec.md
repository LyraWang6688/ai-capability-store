# 规格依据与实测记录

## 1. 这些数字是怎么来的

规格不是拍的，是对一篇真实上线的公众号文章动图做**逆向实测**得出的
（《DeepSeek 为什么敢卖这么便宜？它把答案开源了》，2026-10-20，共 6 张动图）。

| 指标 | 实测值 | 本 skill 采用 |
|---|---|---|
| 尺寸 | 720×540（6 张完全一致，4:3） | 同 |
| 格式 | GIF89a，256 色全局调色板，`NETSCAPE2.0` 无限循环 | 同 |
| 帧率 | 精确 12.5 fps（每帧 80ms） | 同 |
| 时长 | 6.88–8.24s | 6–11s |
| 体积 | 133–342KB | 目标 ≤400KB |
| 底色 | `rgb(249,248,245)` 暖白 | 同 |
| 强调色 | `rgb(168,78,60)` 砖红 | 同 |
| 8×8 块效应 | 无 → 排除"视频转码"链路 | 逐帧直出，天然无块效应 |

## 2. 为什么是 720×540

公众号正文可用宽度约 677px。720×540 是 4:3，等比缩到 677px 宽约 508px 高，
**几乎不触发微信的二次压缩**，同时保留足够字号可读性。

更大的画布（如 1080×810）在同清晰度下体积会翻倍，收益很低。

## 3. 为什么是 12.5fps

- 12.5fps（80ms/帧）对"游标移动、柱条填充、数字跳动"这类节奏**已经够顺**
- 升到 30fps 时，同内容体积约翻倍，而肉眼几乎无感
- 12.5 也是多个 GIF 录制器的默认值，兼容性好

## 4. `optimize=True` 的真相（最容易误判）

Pillow 保存 GIF 时若开启 `optimize=True`，会**合并连续相同帧并把时长累加**。
于是：

```
生成的 frames 列表长度 ≠ GIF 里实际的帧数
"帧数 × 80ms" ≠ 总时长
```

例：demo 柱状图生成 140 帧，实际写入 75 帧，但总时长仍是 11.20s
（92% 的帧为 80ms，少数为 160/560/960/1760/2080ms 的合并帧）。

**要校验时长，只能读 GIF 的 Graphic Control Extension（GCE）块**：

```python
import struct
d = open(path, 'rb').read(); i = 0; delays = []
while True:
    j = d.find(b'\x21\xf9\x04', i)
    if j < 0: break
    delays.append(struct.unpack('<H', d[j+4:j+6])[0] * 10)  # 单位: ms
    i = j + 8
print(sum(delays) / 1000, 's')
```

> 注意偏移量：GCE 头是 `21 F9 04`，延时字段在 `j+4..j+6`。写成 `d[4:6]`
> 会读到文件头，得到荒谬的时长。

## 5. 中文字体

Pillow **无法打开** `/System/Library/Fonts/PingFang.ttc`（新版 TTC 容器格式，报
`cannot open resource`）。可用替代：

```
/System/Library/Fonts/Hiragino Sans GB.ttc   ← 首选，字形接近
/System/Library/Fonts/STHeiti Light.ttc
/Library/Fonts/Arial Unicode.ttf
```

脚本按上表顺序自动探测，全部失败才报错。

## 6. 为什么不录屏/不转视频

两种错误链路都会留下痕迹：

| 链路 | 后果 |
|---|---|
| 录屏 → GIF | 可能带光标、窗口边框；区域尺寸不一致 |
| 视频（H.264）→ GIF | 留下 8×8 块效应与蚊噪，文字边缘发脏 |

逐帧直出 GIF 没有这两类问题。判断别人动图是否走过视频链路：
**测 8px 边界梯度 vs 块内梯度的比值**，明显 >1.5 就是块效应。

## 7. 体积超标的处置顺序

1. 减少动画帧数（`n_anim` / `seg_anim` / `per_step`）
2. 缩短末尾 hold
3. 降低画面元素密度（少一层网格、少一个标注）
4. 仍超标再考虑降到 640×480

不要先降帧率——12.5fps 已是下限区间。
