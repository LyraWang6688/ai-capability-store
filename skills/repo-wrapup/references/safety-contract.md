# 安全契约 · 什么能删，什么不能删

> 这份文件的目的是**让「该不该删」变成机械判断**，不需要 agent 自己权衡。

## 零、总原则：沉默的零 ≠ 确认的零

```
留一个多余的分支   → 下次还能删        便宜的错
说一声"干净了"     → 人就不看了        昂贵的错
```

**一个体检工具最大的风险不是漏删，是让人相信已经没有东西需要看了。**

所以：**判断不了的，必须显式计入 `UNKNOWN` 并列出**，
不得因为「我没有依据」就当「没有」。

> 这条是 2026-10-19 一次 review 补上的。当时 `safe_cleanup.sh` 有个盲区：
> **`git branch --merged` 看不见 squash 合并**——squash 重写了提交，
> 分支 HEAD 不再是 base 的祖先。而本仓库主要用 squash 合并。
> 结果：六个数字全是 0，报告说「干净」，但分支就躺在那儿。

## 一、可以安全删除（全部满足）

`safe_cleanup.sh` 的判定条件，缺一不可：

| # | 条件 | 检查方式 |
|---|---|---|
| 1 | **已推送** | 有上游且 `upstream..branch` 提交数为 0；无上游时 `base..branch` 为 0 |
| 2 | **已合并（双判据）** | 是 `base` 的祖先 **或** 对应 PR 状态为 `MERGED`（`gh pr list --state all`） |
| 3 | **没有 open PR** | 对应 PR 状态不是 `OPEN` |
| 4 | **未被占用** | 不是当前分支；不在 `git worktree list` 的 branch 列表里 |

全部满足 → 进「可安全删除」候选。

> **为什么要双判据**：只查祖先关系时，squash 合并的分支会被判成「既没合并、也没未推送」，
> 然后**静默消失在任何分类之外**。双判据 + UNKNOWN 兜底，才能保证「看不到的东西会说话」。

## 二、绝对不能删（硬禁止）

| 对象 | 原因 |
|---|---|
| 当前分支 | 会把自己所在的分支删掉 |
| `main` / `master` | 主干 |
| 含未推送提交的分支 | **会丢工作** |
| 被 worktree 占用的分支 | 那个 worktree 可能正被别的 agent 使用 |
| 别人的 worktree | 误删不可逆；不确定就留 |
| 有任何未提交改动的 worktree | 同上 |

## 三、worktree 为什么一律不自动删

三个理由：

1. **可能有未提交改动** —— 一旦移除，改动就没了
2. **可能正被另一个 agent 使用** —— 多 agent 并行时分不清
3. **移除是本地操作，没有远端副本可恢复**

> 所以 `safe_cleanup.sh` **只报告 worktree，不删除**。
> 需要清理时，由人判断后手动执行 `git worktree remove <path>`。

## 四、误删的后果比留垃圾严重

这是本契约的总原则：

```
留一个多余的分支   → 下次还能删
误删一个有活的分支 → 工作没了
```

**所以所有边界情况一律「不删，报告」。**

## 五、示例：一次典型判断

```
分支 feat/foo
  ├─ 已推送？      是（无 ahead 提交）
  ├─ 已合并？      是（--merged 命中）
  ├─ 被占用？      否（不在 worktree 列表）
  └─ 结论：可删除 ✅
```

```
分支 fix/bar
  ├─ 已推送？      否（ahead 3 个提交）
  └─ 结论：跳过 ❌ → 列入「含未推送提交 · 不删」
```

```
worktree /path/to/wt  [chore/baz]
  └─ 结论：一律只报告，不删除 ⚠️
```
